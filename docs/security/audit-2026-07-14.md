## Root causes (fix these, not the symptoms)

**RC1 — Soft-delete boundary ignored by the helpers** (#1, #2, #11).
`is_workspace_member` / `has_workspace_role` check `workspace_members.removed_at` but never join `workspaces` to check `deleted_at is null`. Every child table (`tasks`, `audit_events`, `workspace_invitations`, `subscriptions`, `workspace_members`) trusts the helper, so a member of a soft-deleted workspace keeps full read/write for the life of the row. Only `workspaces` itself hides deleted rows.
**Fix:** add `join public.workspaces w on w.id = m.workspace_id and w.deleted_at is null` inside both helpers, and gate the `members_select` self-disjunct on the same liveness. One change closes #1, #2, and #11. *(This is exactly the sibling project's `0060` fix.)*
**Verified:** seeded a task into the soft-deleted `archived` workspace → alice (its owner) read it (count 1) **and** inserted a new task into it (should be 42501). Her membership row was also visible.

**RC2 — Cross-row invariants enforced with a non-locking `count(*)` under READ COMMITTED** (#3, #4, #16).
Both `enforce_last_owner` and `enforce_seat_cap` count without taking any lock. `deferrable initially deferred` does **not** save them — two transactions can each evaluate the deferred check while the other is still open and both pass.
**Fix:** `perform pg_advisory_xact_lock(hashtextextended(_workspace_id::text, 0));` at the top of each trigger (a distinct salt per trigger, or share one per workspace). Advisory — **not** `SELECT … FOR UPDATE` on `workspaces`, which would create a members→workspaces lock-order deadlock (#3-caveat). Also forbid `workspace_id` mutation on a membership row (#16). *(This is the sibling project's `0140`→`0160` advisory-lock fix, including the deadlock lesson.)*
**Verified:** two sessions, each staging a demotion + `SET CONSTRAINTS ALL IMMEDIATE` while the peer was open → **0 owners**. Same shape on seats → **4 active members on a 3-seat free plan**.

**RC3 — Membership write is a non-atomic, non-liveness-aware bare insert** (#6).
`invite-accept` does a plain `insert` into `workspace_members`; re-adding a soft-removed member collides on the composite PK and surfaces `already_member` forever, while `invite-create`'s probe filters `removed_at is null` and doesn't see them. No path clears `removed_at`.
**Fix:** one atomic RPC — `insert … on conflict (workspace_id,user_id) do update set role = excluded.role, removed_at = null, joined_at = now() where workspace_members.removed_at is not null;` — treat 0 rows as `already_member`. The `where removed_at is not null` guard also prevents the naive-upsert trap of silently re-roling an **active** member. *(Sibling project's `0180` RPC.)*
**Verified:** seeded a soft-removed member, bare re-insert → `23505`.

**RC4 — Trust boundaries in the billing / audit-writer / step-up layers** (#5, #7, #8, #12–15).
- Audit **forgery** (#5): the writer role's INSERT is `with check (true)`; integrity is enforced only in TypeScript. On app compromise (or a leaked writer credential) an attacker forges audit history for any tenant — defeating the headline "tamper-evident trail" claim. *(Tamper of existing rows is genuinely blocked — no UPDATE/DELETE for anyone — only **forgery of new rows** is open.)* **Verified:** as `cb_audit_writer`, inserted an event with `actor_id` = a user not in the target workspace → succeeded.
- Stripe **tenant-spoof** (#7): resolve the workspace from the stored `stripe_customer_id → workspace_id` mapping, never from attacker-influenceable `subscription.metadata.workspace_id`.
- Step-up **brute-force** (#8): add `attempts`/`locked_at` to `step_up_codes` (schema-confirmed absent) + a per-actor rate limit; consider an 8-digit code.
- Pin `verify_jwt` per function (#12), pin the cron `search_path` (#13), make idempotency claim+apply transactional (#14), and stop trusting payload metadata for dunning (#15).

**RC5 — DB-vs-app-layer enforcement gaps** (#9, #10).
Reserved-slug and `created_by`-immutability live only in application code / are unconstrained, so a direct PostgREST write (which `authenticated` is granted) bypasses them.
**Fix:** `and not app_private.is_slug_reserved(slug)` in the `workspaces_insert`/`_update` WITH CHECK; pin `created_by` immutable via a BEFORE UPDATE trigger. **Verified:** hostile claimed the `admin` slug and re-attributed `created_by` via direct authenticated writes.

## Recommended remediation order

1. **RC1** (one migration, closes 3 findings) and **RC2** (one migration, closes the two reproduced concurrency HIGHs) — highest severity, smallest diffs, both are proven patterns from the sibling project.
2. **RC3** invite RPC (#6) and **#5** audit-writer hardening.
3. **#7 / #8** — the Stripe tenant-spoof and step-up brute-force (both HIGH, both outside the pgtap suite's reach today).
4. RC5 (#9, #10) and the remaining MED webhook/cron items.
5. LOW hygiene (#17–21).

Each fix should ship with a red→green pgtap test; the existing suite has **zero** coverage of the soft-delete dimension, the two write-skews, or audit forgery — that blind spot is why this class survived to a shipped template.

Definer `search_path=''` pinning on every `app_private.*` function (CI-enforced); no `using(true)`/RLS-off tables; audit-row **tamper** blocked (no UPDATE/DELETE for any role); invite token entropy/hashing/constant-time compare/single-use/expiry/email-binding/server-controlled-role; client cannot write billing state; Stripe signature verified before side effects; cross-tenant audit **read** scoping; self-impersonation CHECK; trigger op-coverage; the soft-delete floor exemption is not abusable into a live ownerless workspace.
